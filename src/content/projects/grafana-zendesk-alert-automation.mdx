## Context

An alert is only the start of support work. Someone still needs to identify the site, find the right contacts and work out whether the same incident already has a ticket.

## What I built

- **Fast ingestion:** a webhook hands alerts to SQS before slower contact and ticketing calls begin.
- **Incident state:** DynamoDB tracks alert-to-ticket mappings and repeated deliveries.
- **Support context:** ticket templates include useful site details, contacts, severity and monitoring links.
- **Operational visibility:** a FastAPI/React dashboard exposes incident state, filters and structured logs.

## Design decisions

Retries should not create a fresh incident every time. Stable alert keys and conditional state writes keep repeated deliveries tied to the existing ticket. Selected alert types can also group multiple affected devices at one site.

A resolved monitoring signal does not automatically close the support ticket. The system preserves the distinction between a condition clearing and a person completing the support work.

## Project overview

The application connects Grafana, AWS serverless services and Zendesk through an asynchronous workflow. It includes status callbacks, merged-ticket handling, optional notifications and a read-side dashboard. Dry-run and controlled test modes support changes before enabling external writes.

The intended benefit is simpler triage: fewer repeated incident records and less manual context gathering. The implementation demonstrates those mechanisms; handling-time and incident-volume improvements have not been quantified.
