## Context

Field devices need a repeatable path from a new Raspberry Pi to a configured, observable system. Assignments change, connectivity is imperfect and remote updates need an understandable result.

## What I built

- **Bootstrap workflows:** operator interfaces and SSH/SFTP tooling for preparing devices.
- **Device agents:** reconcile desired configuration, report state and connect local services with MQTT.
- **Fleet interfaces:** an API, CLI and web tooling around device metadata and AWS IoT workflows.
- **Update handling:** versioned release artifacts, integrity checks and service-restart steps.

## Design decisions

Desired configuration and reported state are separate. A cloud request should not imply that a device has already applied it.

Update jobs similarly need an explicit artifact, verification and execution path. S3 carries release files, IoT Jobs coordinates delivery, and device-side agents report what happened. Operator tools remain part of the design because provisioning and recovery still involve real hardware.

## Project overview

This is a family of cooperating tools rather than one application. It spans Python agents, bootstrap helpers, a TypeScript fleet layer, metadata services and operator views. AWS IoT shadows and jobs connect the device side with cloud workflows, while DynamoDB and S3 provide supporting state and artifacts.

My attributable work includes bootstrap and fleet integration, device-agent changes and operator tooling. Existing Pi scripts and imported operations utilities remain distinct dependencies. The result is a practical device-management foundation; deployment scale and fleet-wide outcomes are not claimed here.
