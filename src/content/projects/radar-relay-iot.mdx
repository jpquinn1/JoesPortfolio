## Context

A range radar sometimes needs a hard power cycle, and the site may be hours away. A small controller beside the radar can do it through a relay. Remote power control raises the stakes, though: a bug, a lost network or a bad update must never leave a radar switched off.

## What I built

- **Controller firmware (C++):** a power state machine for an Arduino Opta driving an industrial relay. It runs an 8-second hardware watchdog, with a breadcrumb in RTC memory before every blocking call. It reads RS-485 temperature and humidity sensors. An ESP32-S3 port on ESP-IDF provisions, reports and updates, with relay switching deliberately left off.
- **Cloud connection:** zero-touch provisioning through Azure's Device Provisioning Service, then MQTT over TLS to IoT Hub, carrying heartbeats, events and device twins. Power cycles are commands with their own lifecycle.
- **Signed over-the-air updates:** ES256-signed release manifests, resumable HTTPS downloads and an MCUboot test swap. A new image confirms itself only after three minutes of healthy watchdog feeding, a live cloud session and a completed twin exchange. Otherwise it reverts. Fleet rollouts go one controller at a time, canary first, and pause automatically on a failure.
- **Network failover:** Ethernet stays preferred. When it can't reach the cloud, the controller moves to a Wi-Fi backup and moves back once Ethernet is healthy.
- **Backend and dashboard:** TypeScript Azure Functions, Cosmos DB and Event Hub ingestion behind a React operator dashboard, covering sites, assignment, commands, firmware jobs and connection history.
- **Commissioning app:** a Python desktop installer that flashes over USB (DFU), verifies signed releases, provisions the board step by step and prints QR labels. A simulation mode uses fake boards and a fake backend.
- **Delivery:** Terraform for the Azure resources, and CI that runs host tests, Opta and ESP32 builds, and link-time guards; for example, the update code cannot reach the relay driver.

## Design decisions

Radar power has to fail safe. The relay's normally closed contact carries the radar's power, so a dead or unplugged controller leaves the radar on. Every boot ends with the radar on, and the hardware layer limits any off period to 120 seconds. An interrupted power cycle is never resumed.

Bench debugging shaped much of the design:

- A breadcrumb identified an MQTT reconnect that hung during a firmware download, so the reconnect was moved out of the download's way.
- The MQTT client mishandled the zero-length acknowledgements IoT Hub sends, and dropped the first byte of the next packet.
- A TLS session to blob storage outlived the watchdog, so it moved to its own thread.
- A socket reader starved the flash-storage worker until its priority was raised, which an A/B run on hardware confirmed.
- Reporting power state only on change cut traffic from about 18,800 to 1,500 messages a day.

## Where it stands

Two Opta controllers and one ESP32-S3 run in a test Azure environment, and one controller has run at a range during a first field release. On the bench, signed OTA updates have succeeded through the deployed backend and dashboard. The Opta has failed over from Ethernet to Wi-Fi in about 3 seconds, the ESP32-S3 in about 9. Firmware, backend, dashboard and installer carry roughly 2,700 automated tests between them.

Not done yet: physical site acceptance, a one-hour soak, relay endurance testing, measured confirmation that the radar actually has power, backup power, and any production rollout.
