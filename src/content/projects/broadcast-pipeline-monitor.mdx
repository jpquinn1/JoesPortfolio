## Context

A device can be reachable while its data stops somewhere farther along a broadcast pipeline. Comparing the outputs of neighboring services helps narrow the investigation.

## Project features

- **Session-based monitoring:** connect a Tour Server feed with an optional paired data-processor feed.
- **Message correlation:** distinguish matching, late and missing observations.
- **Live interface:** stream session and comparison updates to a React dashboard through SignalR.
- **Support context:** combine configuration intent, health checks and bounded container-log views.

## Design decisions

Each monitoring session owns its endpoint pair and history. Comparison results are explicit observations, rather than a single opaque health indicator.

Logs also need limits. Bounded buffers and optional capped persistence keep a diagnostic tool from growing without control. DynamoDB storage and a local development setup support inspection of past observations as well as the current stream.

## Project overview

This local application combines ASP.NET Core, WebSockets, SignalR and React, with Docker-based development and AWS infrastructure definitions. Its role is to observe an existing broadcast system, not produce the underlying shot data.

The interface is designed around practical questions: did both services see the same message, which one was late, and does the current configuration explain the difference? The support views connect those questions with per-device pipeline information and recent logs.

The source is an implemented prototype. The application and infrastructure can be examined locally, while broader deployment and operational impact remain separate from the current case study. This project complements the more focused alert automation and field-equipment monitoring work.
